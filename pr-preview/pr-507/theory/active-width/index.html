    Active-Width Scheduling¶

    The order of commuting operations can change how much active state Clifft needs during sampling. ActiveWidthSchedulePass searches for an order that reduces peak active width, then estimated dense work, while preserving the sampling distribution. It is opt-in and runs after fusion and squeezing. The extra compilation work is intended to save time and memory across many shots.

    For setup, see Compile-time scheduling. For the underlying simulation model, see the Theoretical Overview.

    Why Order Matters¶

    Clifft stores the non-Clifford part of a trajectory in an active array of \(2^k\) amplitudes. A non-Clifford rotation can increase the active width \(k\); a measurement can return an active coordinate to the dormant state and reduce it. Moving a measurement earlier, or delaying a commuting rotation, can therefore reduce the state that must be stored and processed between them.

    The scheduler tracks this width from the Pauli operations in the Heisenberg IR without simulating amplitudes. Its structural model is the same one used by the sampling planner: it tracks a subspace \(S\) of dormant stabilizers, with \(k = n - \dim S\) for an \(n\)-qubit circuit. The prediction does not discover extra stabilizers that might arise from particular amplitudes or rotation angles.

    Only rotations and measurements move. Classical dependencies remain intact, and expectation-value queries and transition instruments act as barriers. Reordering preserves the output distribution, but need not produce identical samples for the same random seed.

    By default, operations may also move across Pauli noise. The compiler keeps track of their original positions relative to noise and corrects their symbolic signs accordingly. This uses the same random noise events as the original circuit; execution makes each event available before an operation needs it. See Planning Pauli-Frame Effects as Symbolic Signs for how these signs are represented.

    Understanding the Result¶

    The pass compares schedules using two quantities, in this order:

    1. Peak active width, which controls the largest active array and is an indicator of memory use.
    2. Estimated dense work, the sum of \(2^w\) over operations that touch the active array, at the width \(w\) where they run. This distinguishes schedules with the same peak but different amounts of work at high widths.

    The pass applies a new order only if peak width falls, or if peak width is unchanged and estimated dense work falls. A tied or worse candidate leaves the input unchanged. A lower peak can therefore be accepted even if its dense-work estimate rises.

    Neither metric measures elapsed time. Record processing, noise sampling, and other fixed costs can dominate small active arrays, and the search does not guarantee a globally optimal schedule. Benchmark compilation and sampling on your circuits before adopting the pass for a workload.

    The pass exposes incumbent_peak, result_peak, incumbent_dense_work, result_dense_work, and applied after it runs. The compiled program's peak_active_width reports its planned peak. Use active_width_trace to inspect how width changes through an HIR; see the Python API.

    Compilation Tradeoff¶

    Run the pass last, after PeepholeFusionPass and StatevectorSqueezePass. Reordering across noise can prevent subsequent peephole fusion.

    By default, the pass skips search when the input peak width is 2 or less: these small active arrays are already cheap to process. Set min_peak_width=0 to search them too. This is a compilation-cost heuristic; it can skip possible improvements on small circuits.

    The default beam_width=8 explores several partial schedules at once. A smaller beam reduces search effort; a larger one explores more alternatives but does not guarantee a better result. The deterministic search_budget=16 limits search executions relative to circuit size and progressively narrows the search to greedy choices. search_budget=0 requests greedy continuation; search_budget=None disables budget-driven narrowing.

    The budget bounds executions, allowing ongoing sweeps to finish; it does not bound classification probes or wall time. On circuits with many independent rotations, repeatedly checking available choices can require quadratic work. The statistics swept_ops and classification_probes distinguish executed operations from these checks. Graph construction and final analysis also add to compilation cost.

    The extra compilation cost is paid once per compiled program. It is most likely to be worthwhile when a lower width or less dense work saves time across many shots. For a short sampling run, omitting the scheduler may be faster overall even when scheduling improves the active-width metrics. See the CPU execution guide for how to select that pipeline.
