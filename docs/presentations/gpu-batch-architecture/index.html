The 0.8 reset

Clifft removed the SVM, not just its opcodes

Before 0.8
Circuit + localized-Pauli lowering
Public SVM bytecode
Scalar / AVX interpreters

The VM encoded localization steps and kept several interpreters on one instruction contract.

0.8 and later
Circuit → optimized HIR
SamplingPlan
CPU ExecutablePlan → Executor

Planning resolves coordinates, Pauli shapes, branches, and dependencies before a shot runs.

The current action tape is private prepared data. It is not stable bytecode and does not preserve the old SVM vocabulary.
The old SVM was a sound design for localized Pauli execution, but the symbolic sampler no longer needs localization instructions. Direct multi-coordinate kernels and symbolic branch expressions made the old VM a second representation with no required capability. Sources: docs/updates/symbolic-sampling.md and docs/theory/architecture.md.

Execution strategy

Batch CPU and GPU should evolve together

CPU strategies

  • serial shots
  • shot-parallel workers
  • OpenMP within wide kernels
  • packed cross-shot batches
selector observes the workload

GPU strategies to measure

  • one thread per shot near k = 0
  • one group per shot at small k
  • coefficient-parallel work at larger k
Public names stay simple: cpu, cuda, rocm. Strategies remain internal, with an expert override.
One CPU resource budget: coordinate shot workers and OpenMP threads so N workers do not each start M kernel threads.
This avoids proliferating public types such as CPUSampler and CPUBatchSampler. The same prepared-execution boundary supports both packed CPU batches and GPU contexts. The selector can use shot count, active-width history, action mix, postselection, outputs, precision, memory, and preparation cost. Sources: Discussion 382 and PR 379.

First usable slice

The first release is intentionally narrow

Must work

  • Linux x86-64, one synchronous GPU
  • FP64 and explicit backend selection
  • sample and survivor sampling
  • postselection and record output
  • EXP_VAL, if the spike confirms feasibility
  • unchanged CPU default and install

Defer

  • leakage and loss
  • sample_k and importance sampling
  • exact state and probability queries
  • multi-GPU and asynchronous APIs
  • FP32 and automatic backend choice
  • a stable public GPU bytecode
Representative hardware
NVIDIA: H200-class performance target; L40S-class optional correctness/CI target
AMD: start on MI300X / gfx942; add gfx950 with hardware access
Initial workloads are magic-state cultivation and distillation. H200 offers a strong FP64 performance target; L40S can be a lower-cost functional target but should not stand in for FP64 performance. AMD's mapping establishes two device-code targets: MI300X/MI325X use CDNA 3 / gfx942, while MI350X/MI355X use CDNA 4 / gfx950. Available MI300X credits make gfx942 the real phase-0 hardware path. We should compile for gfx950 but not claim correctness or release support until MI350X/MI355X hardware is available. Sources: Discussion 382; AMD partner input; https://rocm.docs.amd.com/en/latest/reference/gpu-specs.html

Maintainability

Correctness does not require a GPU on every PR

CPU oracle Every PR

Action lowering, descriptor validation, forced trajectories, deterministic EXP_VAL, negative tests, and device-code compilation.

Trusted device smoke Relevant PRs

Small CUDA and ROCm runs on controlled branches; no arbitrary fork code on scarce hardware.

Broad device suite Main + scheduled

Statistical CPU comparisons and realistic circuits on gfx942 first; add gfx950 when hardware is available.

Release matrix Before publishing

Runtime family, driver floor, each advertised device-code target, wheel install, and end-to-end workload checks.

Cross-backend bit-for-bit seeds are not required. Each GPU backend should be reproducible across batching and launch choices.

The CPU implementation remains the trusted semantic oracle. Most bugs can be caught without hardware by validating lowering and executing forced paths. Device CI then answers the questions a CPU cannot: compilation against the real toolchain, launch correctness, memory behavior, and numerical/statistical agreement. Start real AMD smoke and scheduled testing on MI300X / gfx942. Keep gfx950 compile-only until hardware exists; if gfx950 is later advertised, scheduled and release coverage must include a real gfx950 device. Sources: Discussion 382; https://rocm.docs.amd.com/en/latest/reference/gpu-specs.html

  • No silent fallback after a user explicitly requests a GPU.
  • Capability errors explain the missing operation or unsupported target.
  • An execution report exposes the selected backend, strategy, device, precision, and memory plan.
  • One ROCm wheel can later bundle gfx942 and gfx950 after both targets are device-validated.

Package names are illustrative. Companion packages add wheel work, but the matrix stays bounded by supporting one runtime family per vendor and Linux x86-64 only. HIP-Clang can generate a fat binary with a code object for each device target, so gfx942 and gfx950 do not require separate Python distributions. The first experimental package may advertise gfx942 only if that is the only target validated on real hardware; gfx950 can be added to the same package later. A private versioned C boundary or capsule can connect the companion package without making the prepared representation public. Experimental packages

The spike is deliberately basic and isolated. It should answer layout, launch, precision, postselection, and shot-count questions before we freeze a shared GPU representation.
Phase 0 can be owner-led to preserve a high quality bar while collaborators explore. It needs only a minimal boundary and CPU-oracle validation. Phase 1 turns what we learned into a maintainable product boundary and develops packed CPU batching alongside it. Source: Discussion 382.

Discussion and next step

Start now; keep the support matrix open

  1. Architecture: agree on one semantic plan, native target preparation, and explicit Python backend selection.
  2. AMD: activate MI300X credits, confirm ROCm and driver floors and an owner, then identify a path to gfx950 hardware.
  3. Unitary Foundation: confirm first workloads, maintenance ownership, trusted hardware policy, and release expectations.
  4. NVIDIA follow-up: validate the H200/L40S-class split and answer the same runtime, CI, and ownership questions.

Proposed decision

Start phase 0 with explicit exit criteria.

Use its evidence to finalize the backend boundary, first device matrix, and sequence of implementation PRs.

AMD's device-code mappings are no longer open: gfx942 covers MI300X/MI325X and gfx950 covers MI350X/MI355X. MI300X credits provide the starting hardware path for gfx942. ROCm and driver floors, CI integration, maintenance ownership, and access to a gfx950 device remain open. These do not block the architecture or gfx942 spike, but gfx950 cannot enter the support or release matrix without real-device validation. Close by asking whether the group agrees to start phase 0 and who owns each remaining vendor input. Sources: Discussion 382; AMD partner input.
